## 1. PURPOSE

Implement the receiving functionality for geographic discoveries transferred from **4nR-CRONKITE** using its `SEND TO NERDS` command.

The integration must allow CRONKITE discoveries to be presented as proposed waypoints within the existing NERDS interface without interfering with approved expedition routes or navigational calculations.

NERDS remains responsible for waypoint management, approval, ordering and routing.

CRONKITE remains responsible for identifying discoveries and initiating their transfer.

**The user retains absolute control over whether a discovery becomes an approved routing waypoint.**

## 3. WAYPOINT RECEPTION

When NERDS receives a valid CRONKITE discovery:

1. Create a new waypoint using the discovery's geographic coordinates.
2. Insert the waypoint at the **TOP of the current waypoint list**, regardless of existing waypoint order.
3. Identify its source as `4nR-CRONKITE`.
4. Set its initial status to `AWAITING APPROVAL`.
5. Preserve the CRONKITE discovery ID, event name, category, date/time, description and source references wherever supplied.

The receiving mechanism must respect existing NERDS waypoint data structures and user-project persistence requirements.

**Important:** The pending waypoint's position in the visible list must not automatically determine its participation in the active calculated route.

## 4. VISUAL IDENTIFICATION

Pending CRONKITE waypoints must:

- Flash **yellow-orange at 1 Hz** (one complete cycle per second).
- Display the caution indication on both the waypoint map marker and the waypoint list entry.
- Display `AWAITING APPROVAL` as readable text.
- Remain visually distinguishable from existing red CHEKHOV navigational warnings.

The caution indication must clearly communicate that the waypoint is a proposed discovery awaiting user approval.

Its colour, animation and presentation must not be confused with navigational danger, routing failure or confirmed geographic restrictions.

The implementation must preserve normal waypoint visibility and interaction.

## 5. ROUTE PROTECTION

While awaiting approval:

- The waypoint must not participate in active route calculations.
- It must not change existing route geometry or sequencing.
- It must not trigger automatic route recalculation.
- Its presence must not constitute navigational approval.

NERDS must explicitly distinguish:

**A. Waypoint display order**

The waypoint's position in the user-visible list.

**B. Waypoint approval status**

Whether the user has accepted the proposed discovery.

**C. Route participation**

Whether the waypoint is eligible for inclusion in the actual calculated route.

These are separate properties.

A pending waypoint may be displayed, inspected and reordered without becoming an active navigation waypoint.

All routing functions must continue to exclude unapproved CRONKITE discoveries, regardless of their position in the waypoint list.

## 6. USER INTERACTION

Provide the following waypoint context-menu commands.

### APPROVE WAYPOINT

- Changes the waypoint to approved status.
- Stops the flashing caution indication.
- Applies standard NERDS waypoint styling.
- Makes the waypoint eligible for normal route planning.

Approval must be explicit.

Approval must not silently replace an existing route or override the established user-controlled routing workflow.

### REJECT WAYPOINT

- Removes the pending waypoint from the current waypoint list and map.
- Does not alter the existing route.

Rejection must not remove or modify unrelated waypoints.

### DRAG AND DROP

- Users can reposition the pending waypoint anywhere in the waypoint list.
- Reordering does not constitute approval.
- A pending waypoint remains excluded from route calculations regardless of its list position.

Existing NERDS drag-and-drop behaviour for ordinary waypoints must remain operational.

### STATUS PERSISTENCE

Approval status, source identification and associated discovery metadata must remain consistent with the application's existing waypoint persistence and project-management mechanisms.

Do not allow project reloads, list refreshes or map redraws to bypass the pending-approval requirement.

## 7. TRANSFER INTEGRITY

- Preserve the original CRONKITE discovery identifier.
- Prevent accidental duplication when the same discovery is transferred repeatedly.
- Validate received coordinates and required identification fields.
- Report failed or invalid transfers without corrupting the current waypoint list.

Repeated transfers must not create uncontrolled duplicates or change existing routes.

Malformed or incomplete transfers must be rejected safely and reported appropriately.

Preserve source attribution and available event references for subsequent inspection.

Do not fabricate missing metadata.

The contract must support:

| Field | Requirement |
|---|---|
| Source application | `4nR-CRONKITE` |
| Discovery identifier | Required; preserve original |
| Geographic latitude | Required; validate |
| Geographic longitude | Required; validate |
| Event/discovery name | Required |
| Category | Preserve when supplied |
| Date/time | Preserve when supplied |
| Description | Preserve when supplied |
| Source references | Preserve when supplied |
| Initial NERDS status | `AWAITING APPROVAL` |

The receiving interface must be capable of distinguishing newly transferred discoveries from previously received discoveries.

Coordinate validation must reject invalid geographic values.

The contract must establish predictable responses for accepted, duplicate, invalid and failed transfers.

Document the proposed transport mechanism and any architectural decisions requiring approval before introducing new external dependencies.

## 11. REGRESSION TESTING

Develop automated tests covering the following behaviours.

### A. Discovery reception

- Valid discovery accepted.
- Invalid coordinates rejected.
- Missing required identification rejected.
- Source information preserved.
- Available metadata retained.

### B. Initial presentation

- New discovery appears at the top of the current waypoint list.
- New map marker is created.
- Source `4nR-CRONKITE` is displayed.
- Status `AWAITING APPROVAL` is displayed.
- Yellow-orange caution animation operates at 1 Hz.
- The map marker and waypoint list entry are visually consistent.

### C. Route isolation

- Pending waypoint is excluded from route calculations.
- Existing route geometry remains unchanged.
- Existing route order remains unchanged.
- No automatic recalculation occurs.
- Dragging a pending waypoint does not alter the active route.

### D. Approval

- Explicit approval changes status.
- Flashing stops.
- Normal styling is applied.
- Waypoint becomes eligible for ordinary routing.
- Existing routing safeguards remain operative.

### E. Rejection

- Pending waypoint is removed from the list.
- Pending map marker is removed.
- Existing route remains unchanged.
- Other waypoints are unaffected.

### F. Reordering

- Pending waypoints can be repositioned throughout the waypoint list.
- Approval status remains unchanged after reordering.
- Route calculations remain unaffected while approval is pending.

### G. Duplicates and invalid transfers

- Repeated discovery transfers are detected.
- Duplicates do not create uncontrolled waypoint entries.
- Invalid transfers produce appropriate error reporting.
- Failed transfers leave existing waypoint and route data intact.

### H. Persistence and compatibility

- Saved projects retain appropriate waypoint statuses and metadata.
- Reloading a project does not automatically approve a pending waypoint.
- Existing NERDS projects remain compatible.
- Existing routing regression tests continue to pass.
- CHEKHOV warning presentation remains unaffected.
